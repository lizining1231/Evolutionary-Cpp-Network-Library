分析：
我原先在考虑开销

下次遇到性能问题，先别打开 IDE，拿出一张纸，画：

text
[客户端] 
    ↓ (SYN 包)
[网卡] 
    ↓ (软中断)
[SYN 队列] ← 大小: net.ipv4.tcp_max_syn_backlog
    ↓ (三次握手完成)
[accept 队列] ← 大小: listen(fd, backlog)
    ↓ (accept() 取出)
[进程 fd 表] ← 上限: ulimit -n
    ↓ (epoll_ctl 添加)
[epoll 就绪队列] 
    ↓ (epoll_wait 取出) ← 你的 events[] 数组大小
[你的业务逻辑]
然后问自己：600 个并发时，哪个环节会先满？

SYN 队列默认 128？→ 600 瞬间涌入，满了

backlog 默认 128？→ 满了

fd 限制 1024？→ 600 还没满，排除

events[] 数组 64？→ 一次只能取 64 个，要多轮处理，延迟增加
